## 3. Blocker: antivirus TLS interception (host issue, not a product defect)

`securityadmin` failed with `PKIX path building failed`. Capturing the
certificate the node actually serves:

```
SERVED subject : CN=node-0.example.com, OU=node, O=node, L=test, C=de
SERVED issuer  : CN=Norton Web/Mail Shield Untrusted Root,
                 O=Norton Web/Mail Shield,
                 OU=generated by Norton Antivirus for untrusted server certificates
SERVED thumb   : 7134BB985BC218BBF29FD999ECB3DE29B399A90E
LOCAL  thumb   : D6731572C5858C3921B03F0F17A0F418C8D39CD4   (config\esnode.pem)
```

Norton Web/Mail Shield is MITM-ing loopback TLS on :9200 and re-signing the
node certificate with its own *Untrusted* CA. Java therefore cannot build a path
to `root-ca.pem`. Norton does not publish that CA to the Windows store (by
design), and it also disrupts the HTTP/2 admin channel, so trusting the leaf
directly did not help either.

The same interception broke `git` at the start of this session
("unable to get local issuer certificate"), which corroborates the diagnosis.

**Not a defect in the installer or the product.** To finish these checks, either
exclude port 9200 from Norton's Web/Mail Shield, or run the test on a server
without TLS-inspecting antivirus.

## 4. Defect: `get-fingerprint.ps1` disagrees with the validating plugin

Severity: **High — would make every Windows licence request unusable.**

```
License fingerprint mismatch!
  Licensed for:  d480b59a4fa8ff88cd9672c53cbeca62bf0e91775f0b094e64659fbdcbb27671
  This machine:  691659e84797cd7d3e22021da866ede3661a4c68538a73da2990c634b460e259
```

`get-fingerprint.ps1` — the tool operators are instructed to run in order to
*request* a licence — reported `d480b59a…`. The `MachineFingerprint` class that
*validates* the licence computed `691659e8…` on the same host, at the same time.

Both nominally read CPU ID, baseboard serial and disk-0 serial via the same CIM
classes, so the divergence is in value handling or execution context (the plugin
runs as the service account; the script ran as the interactive user).

Consequence: an operator sends the vendor an MFP the plugin will never agree
with, the vendor issues a licence bound to it, and the node refuses to start.
Confirmed live — the licence generated for the reported MFP was rejected, while
the older `keys/license.key` (bound to `691659e8…`) was accepted.

**Not fixed in this build.** Root-causing requires running both implementations
under the service account, which the antivirus blocker cut short. This should be
resolved before any Windows customer licence is issued.

## 5. Defect: uninstaller destroys a pre-existing Fluentd — FOUND THE HARD WAY

Severity: **High — data loss outside the product's own footprint.**

The test host had Fluent Package v5.0.6 at `C:\opt\fluent`, installed
2025-04-24, unrelated to Supra. The shipped `uninstall.ps1`:

1. searched Add/Remove Programs for `Fluent Package*` / `Td-agent*`,
2. found and silently uninstalled **v5.0.6**,
3. then deleted `C:\opt\fluent` outright.

It never checks whether *it* installed that runtime. On any server where an
operator already ran Fluentd, uninstalling Supra removes their Fluentd too.

This was predicted before running the revert and a guard was written into the
build script — but the **already-packaged** `uninstall.ps1` inside the test
artifact still had the old behaviour, so it executed and removed the runtime.

**Repaired:** the exact version (Fluent Package v5.0.6, fluentd 1.16.7) was
downloaded and reinstalled; `C:\opt\fluent` and its ARP registration are back.

**Fixed in source:** `install.ps1` now drops a `.supra-installed` marker into the
runtime folder, and `uninstall.ps1` removes the runtime only when that marker is
present. *This fix is in `build-installer.ps1` but is NOT in the tested artifact —
rebuild before shipping.*

## 6. Near-Miss: `uninstall.ps1` would have deleted the working tree

`uninstall.ps1` ends with:

```powershell
Get-ChildItem -Path $InstallDir -Force | Remove-Item -Recurse -Force
```

It never verifies that `$InstallDir` is something it created. The obvious install
path on this host was `D:\supra` — which is the operator's working directory
(`Documents`, `OPCServerModbus`, `Projects`, 446,660 items, including this
repository). Windows paths are case-insensitive, so `D:\supra` is `D:\Supra`.

Installing there and reverting would have **deleted the entire Projects tree**.
Caught by inspecting the target before use; `D:\supra-test` was used instead.

**Recommendation (not yet implemented):** `install.ps1` should refuse a
non-empty `-InstallPath` that it did not create, and `uninstall.ps1` should
remove only known subdirectories (`opensearch`, `dashboards`, `log-collector`,
`nssm`) rather than everything it finds.

## 7. Defect: the installation guide's verification commands cannot work

Severity: **Medium — documentation.**

The node negotiates **TLS 1.3**. PowerShell 5.1 runs on .NET Framework, which
does not support TLS 1.3, so every `Invoke-RestMethod` / `Invoke-WebRequest`
example in the guide fails with *"The underlying connection was closed"*,
regardless of `SecurityProtocol` or certificate-validation callbacks.

Verified: raw `SslStream` negotiated `Tls13` successfully, and `curl.exe`
(schannel) connected and completed ALPN, while `Invoke-WebRequest` failed on the
same endpoint at the same moment.

**Fix:** the guide's verification and API sections must use `curl.exe`, which
ships with Windows Server 2019+ and Windows 10/11.
